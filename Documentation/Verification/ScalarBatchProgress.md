# Scalar-batch progress verification

Historical scope: reporting has since been extended to all generation commands.
See [GeneratorProgress.md](GeneratorProgress.md) for the current checks.

Date: 6 October 2026. This report follows the generator migration recorded in
[GeneratorVerification.md](GeneratorVerification.md); that earlier report and
its checksum describe the earlier implementation.

## Scope

Only `GenerateGravitonScalars` gains unconditional reporting. Its specific-order
counterpart, other generator commands and standalone converter calls retain
their existing output behaviour. Calculation options, mathematical definitions,
library filenames and successful/failure return contracts are unchanged.

## Checks

24 focused checks passed in fresh Wolfram kernels.

- A real serial-FORM order-one scalar batch wrote both libraries to a temporary
  directory despite `ShowProgress -> False`, reporting every stage and timing.
- Its two expressions matched those generated by the specific-order command,
  whose previous reporting was also checked.
- A mocked order-five batch verified ten jobs in kinetic/potential order, labels,
  replacement counts and the final summary without computing high-order rules.
- Controlled failures covered missing FORM, construction, writing, timeout and
  publication-success/backup-cleanup-failure. Checks covered stopping the batch,
  completed-file accounting, retained diagnostic paths and no false success.
- A direct abort propagated after an abort summary. Reporter definitions and
  global options were restored after calls; another generator remained quiet
  under the same mocked conditions as before.
- Mocked converter events checked contextual periodic elapsed messages, serial
  fallback and stdout/stderr paths. This did not require a long-running job.

The checks used temporary scripts and output directories. Stored libraries and
example/benchmark notebooks were not regenerated. No Full benchmark or complete
converter regression rerun is claimed for this reporting-only change.
